# Сравнение способов развёртывания TMS

## Критерии

| Критерий | Нативный (LANTMS_linux_1.4) | Docker + Ansible |
|---|---|---|
| Сложность первого развёртывания | Средняя: установка .NET, PostgreSQL, распаковка, systemd | Средняя: установка Docker, сборка образа, запуск контейнера |
| Воспроизводимость | Ручная/скриптовая; зависит от дисциплины | Высокая: образ + плейбук, идемпотентность |
| Требования к инфраструктуре | ОС + .NET + СУБД | ОС + Docker (+ registry) |
| Порог входа для команды (3 чел.) | Ниже: стандартные Linux-навыки | Выше: Docker, Ansible, registry |
| Время развёртывания (оценка) | ~1–3 ч (первый раз) | ~2–4 ч (первый раз) |
| Время отката | Замена архива + рестарт сервиса | Переключение тега образа + перезапуск контейнера |
| Риски для СИБ | Меньше слоёв; стандартный аудит ОС | Нужны политики registry, подпись образов, контроль Docker-хостов |
| Масштабирование (много серверов) | Ручное/скриптовое | Ansible + inventory, одна команда на N серверов |
| Сопровождение | Проще для 1–2 серверов | Оправдано при росте числа серверов/сред |
| Соответствие «как Solar» | Частично (нет Ansible-оркестрации) | Ближе к процессу Solar (Git-теги, Ansible-теги, откат) |

## Вывод (предварительный)

Для текущего ландшафта (1–2 экземпляра) **нативный способ — основной**: меньше зависимостей, проще сопровождать. **Docker + Ansible — пилот** на пре-проде с документацией и передачей знаний; решение о масштабировании — по итогам замеров и готовности команды.
